##01::3
Что такое архитектура приложения?
Структурная организация системы, определяющая компоненты, их взаимодействие и способы расширения
Набор классов для работы с базой данных
Список используемых NuGet-пакетов
Перечень серверов для развертывания приложения
##02::3
Какая цель ставится перед архитектурой приложения?
Масштабируемость, поддерживаемость, тестируемость и отказоустойчивость
Увеличение тактовой частоты процессора
Сокращение объёма исходного кода
Ускорение компиляции проекта
##03::3
Что относится к критериям выбора архитектурного стиля?
Размер и сложность приложения, частота изменений и навыки команды
Цветовая схема пользовательского интерфейса
Разрядность операционной системы сервера
Количество установленных браузеров
##04::3
Что представляет собой монолитная архитектура?
Все компоненты приложения объединены в единый процесс и развертываются вместе
Приложение разделено на независимые сервисы с собственными базами данных
Компоненты обмениваются сообщениями через брокер событий
Каждый модуль развертывается отдельным контейнером
##05::3
Какой недостаток характерен для монолита?
При изменении части приложения приходится пересобирать весь монолит
Отсутствие поддержки баз данных
Невозможность использовать контроллеры
Обязательное использование облачных сервисов
##06::3
Как выглядит типичный пример монолитного приложения на .NET?
Проект ASP.NET Core MVC с контроллерами, сервисами и репозиториями в одном решении
Набор независимых микросервисов, каждый в отдельном репозитории
Приложение, состоящее только из клиентского кода
Скрипт для настройки брокера сообщений
##07::3
Какие слои выделяются в многоуровневой (N-tier) архитектуре?
Presentation, Business Logic и Data Access
Entities, Use Cases, Interface Adapters и Frameworks
Publisher, Subscriber и Broker
Client, Gateway и Load Balancer
##08::3
Что входит в Presentation Layer в N-tier архитектуре?
UI и контроллеры
Работа с базой данных
Бизнес-логика и сервисы
Миграции Entity Framework
##09::3
Какой класс в примере N-tier отвечает за бизнес-логику?
ProductService
ProductsController
ProductRepository
OrderCreatedEvent
##10::3
В чём преимущество многоуровневой архитектуры?
Чёткое разделение ответственности, легче тестировать и поддерживать
Полное отсутствие зависимостей между слоями
Автоматическая масштабируемость без настройки
Отказ от использования базы данных
##11::3
Каков принцип сервис-ориентированной архитектуры (SOA)?
Приложение состоит из отдельных сервисов, взаимодействующих через стандартизированные протоколы
Все компоненты запускаются в одном процессе
Сервисы передают данные только через файлы
Приложение представляет собой один большой проект
##12::3
Через какие протоколы взаимодействуют сервисы в SOA?
HTTP и SOAP
SMTP и POP3
FTP и Telnet
DNS и DHCP
##13::3
Какой недостаток характерен для SOA?
Задержки при сетевых вызовах
Невозможность переиспользования сервисов
Отсутствие поддержки развертывания
Полная зависимость от одного сервера
##14::3
Чем микросервисная архитектура отличается от SOA?
Меньшими независимыми сервисами, каждый разрабатывается, тестируется и развертывается отдельно
Обязательным использованием протокола SOAP
Запуском всех сервисов в одном процессе
Полным отсутствием сетевого взаимодействия
##15::3
Как взаимодействуют микросервисы на ASP.NET Core в примере лекции?
Через HTTP REST или gRPC
Через общую таблицу базы данных
Через общие статические поля в памяти
Через одну сборку библиотеки классов
##16::3
Какой минус микросервисной архитектуры указан в лекции?
Сложность мониторинга и логирования
Невозможность независимого развертывания
Отсутствие поддержки масштабирования
Обязательное использование Windows
##17::3
Через что компоненты обмениваются сообщениями в event-driven архитектуре?
Через брокеры событий, например RabbitMQ или Kafka
Через вызовы методов внутри одного процесса
Через статические классы
Через текстовые файлы на диске
##18::3
Какое преимущество даёт event-driven архитектура?
Асинхронность и слабая связность компонентов
Полное отсутствие задержек
Отказ от внешней инфраструктуры
Автоматическое тестирование
##19::3
Какие слои выделяются в чистой архитектуре (Clean Architecture)?
Entities, Use Cases, Interface Adapters и Frameworks and Drivers
Presentation, Business Logic и Data Access
Controllers, Views и Models
Publisher, Subscriber и Broker
##20::3
Какое утверждение соответствует чистой архитектуре?
Entities не знают про инфраструктуру, а Application Layer не зависит от фреймворка
Контроллеры напрямую работают с базой данных в обход слоёв
Бизнес-логика полностью зависит от выбранного фреймворка
Слой Entities содержит настройки веб-сервера
